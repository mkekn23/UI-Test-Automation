# UI-Test-Automation

ეს პროექტი წარმოადგენს tbcbank.ge ვებ-პორტალის ავტომატიზებულ UI ტესტირებას, რომელიც აგებულია Java 17, Selenide, TestNG და Maven ტექნოლოგიურ სტეკზე. პროექტი ფარავს როგორც Desktop, ასევე Mobile (Responsive) ვერსიების პარალელურ ტესტირებას.

## Why Automate This?
ნებისმიერი UI ავტომატიზაციის მთავარი მიზანია მაღალი რისკის შემცველი და ბიზნესისთვის კრიტიკული ფუნქციონალის ხშირი, სწრაფი და უშეცდომო გადამოწმება. პროექტში ავტომატიზაციისთვის შეირჩა 5 ძირითადი სცენარი:

### 1. KAN-T1: რუკაზე ძებნა ფილიალებისა და ბანკომატების გაფილტვრით
* **რისკი:** საშუალო-მაღალი. არასწორი გაფილტვრისას მომხმარებელს შეიძლება ეჩვენოს დაკეტილი ფილიალი ან ბანკომატი, სადაც არ არის სასურველი სერვისი (მაგ. სავალუტო კასა, 24/7 წვდომა).
* **ბიზნეს ღირებულება:** მაღალი. უზრუნველყოფს კლიენტების სწორ გადამისამართებას შესაბამის ლოკაციაზე და ზოგავს ბანკის ოპერატორების დროს.
* **რატომ UI ავტომატიზაცია?:** ფილტრების კომბინაცია დინამიურად ცვლის DOM-ში ასახულ ლოკაციების სიასა და რუკის მარკერებს. UI ავტომატიზაცია ამოწმებს, რომ ფილტრის ჩართვა/გამორთვა რეალურ დროში სწორად ანახლებს ვიზუალურ კომპონენტებს.

### 2. KAN-T2: რუკაზე კონკრეტული ფილიალის მოძებნა
* **რისკი:** საშუალო. თუ ძებნის ინფუთი არ მუშაობს ან კონკრეტული მისამართის მიხედვით რუკა არ აახლებს მარკერს/ლოკაციას, მომხმარებელი ვერ მიაგნებს სასურველ ფილიალს.
* **ბიზნეს ღირებულება:** მაღალი . ფილიალის სწრაფი მოძებნა ამცირებს მომხმარებელთა კმაყოფილების რისკებს და ეხმარება კლიენტებს ოფლაინ მომსახურების მიღებაში.
* **რატომ UI ავტომატიზაცია?:** მოიცავს Google Maps / MapBox Web Component-ების ინტერაქციას, საძიებო ველში ტექსტის აკრეფას, რომელიმე მისამართის არჩევას და რუკაზე შესაბამისი Pin/Marker-ის გამოჩენის ვიზუალურ ვალიდაციას.

### 3. KAN-T3: ვალუტის კურსის კალკულაცია
* **რისკი:** მაღალი. ვალუტის კურსების ცვლილება დინამიურია. კალკულატორში არასწორი გადაანგარიშება, სავალუტო წყვილის არასწორი არჩევა ან ველების აცდენა იწვევს მომხმარებლის შეცდომაში შეყვანას.
* **ბიზნეს ღირებულება:** კრიტიკული. ვალუტის კონვერტაცია ბანკის ერთ-ერთი ყველაზე მაღალი ტრაფიკის მქონე სერვისია. სწორი კურსის და თანხის მყისიერი ასახვა პირდაპირ მოქმედებს მომხმარებლის ნდობასა და ტრანზაქციების რაოდენობაზე.
* **რატომ UI ავტომატიზაცია?:** სცენარი მოითხოვს დინამიური Real-time ინტერფეისის შემოწმებას, ერთ ველში თანხის შეყვანისას მეორე ველის მყისიერ განახლებას, "Swap" ღილაკით ვალუტების ადგილების გაცვლას და სავალუტო კურსის ცვლილების ასახვას UI-ზე.
  
### 4. KAN-T4: სამომხმარებლო სესხის კალკულაცია სესხის თანხით
* **რისკი:** კრიტიკული. ყოველთვიური გადასახადის ან სესხის ვადის არასწორად გამოთვლა იწვევს დარღვევებს და მომხმარებლის უკმაყოფილებას.
* **ბიზნეს ღირებულება:** კრიტიკული. სამომხმარებლო სესხი ბანკის ერთ-ერთი ყველაზე მომგებიანი პროდუქტია.
* **რატომ UI ავტომატიზაცია?:** სესხის კალკულატორი შეიცავს სლაიდერებს და ინფუთებს. აუცილებელია შემოწმდეს სლაიდერის გადაადგილებისას ინფუთის სინქრონიზაცია, ყოველთვიური შენატანის დინამიური გადაანგარიშება და საპროცენტო განაკვეთის სწორი ასახვა UI-ზე.

### 5. KAN-T5: ფულადი გზავნილის საკომისიოს შემოწმება
* **რისკი:** მაღალი. საკომისიოს არასწორი კალკულაცია ან არასწორი ქვეყნის/სისტემის მიხედვით ტარიფის გამოთვლა ფინანსურ აცდენას იწვევს.
* **ბიზნეს ღირებულება:** მაღალი (High). საერთაშორისო გზავნილები მნიშვნელოვანი ფინანსური ნაკადია. გამჭვირვალე და სწორი საკომისიოს გამოჩენა ზრდის კლიენტების ნდობას.
* **რატომ UI ავტომატიზაცია?:** სცენარი მოიცავს დროპდაუნებიდან ქვეყნისა და ვალუტის არჩევას, თანხის შეყვანას და შესაბამისი ბარათის გამოჩენას საკომისიოს ოდენობით. UI ტესტი ამოწმებს ამ კომპონენტების ერთობლივ გამართულ მუშაობას.

## 2 Selector Strategy - 25 pts

სტაბილური სელექტორები UI ავტომატიზაციის საფუძველია. პროექტში გამოყენებულია სელექტორების იერარქიული სტრატეგია, რათა მინიმუმამდე დავიყვანოთ ტესტების გაფუჭება UI სტილების ცვლილებისას.

### Key სელექტორების ანალიზი:

1. **`app-currency-dropdown[formcontrolname='sellCurrency'] .currency-dropdown__trigger`**
   * **რატომ არის სტაბილური?:** იყენებს Angular-ის ბიზნეს-ლოგიკაზე მიბმულ ატრიბუტს (`formcontrolname='sellCurrency'`). UI დიზაინიც რომ შეიცვალოს, ფორმის კონტროლერის სახელი ბექენდ/ფრონტენდ ლოგიკაში იშვიათად იცვლება.
   * **რამ შეიძლება გააფუჭოს?:** Angular-ის ფორმის რეფაქტორინგმა ან `formControl` ცვლადის სახელის შეცვლამ.

2. **`google-map[mapid='ATM_BRANCHES_MAP']`**
   * **რატომ არის სტაბილური?:** მიბმულია Web Component-ის უნიკალურ `mapid` ატრიბუტზე, რომელიც სპეციალურად რუკის ინსტანციისთვისაა განსაზღვრული.
   * **რამ შეიძლება გააფუჭოს?:** Google Maps კომპონენტის სხვა ბიბლიოთეკით ჩანაცვლებამ.

3. **`a[href*='/other-products/money-transfers']`**
   * **რატომ არის სტაბილური?:** ეფუძნება საიტის როუტინგის URL სტრუქტურას (`href`), რაც ბევრად სტაბილურია, ვიდრე ღილაკის ტექსტური დასახელება (რომელიც ენის შეცვლისას იცვლება) ან CSS კლასები.
   * **რამ შეიძლება გააფუჭოს?:** საიტის URL არქიტექტურის/როუტების გლობალურმა ცვლილებამ.

4. **`tbcx-dropdown-selector button.tbcx-field`**
   * **რატომ არის სტაბილური?:** ეფუძნება TBC-ის Design System-ის custom ვებ-კომპონენტს (`tbcx-dropdown-selector`), რაც უზრუნველყოფს იდენტურ ქცევას ყველა გვერდზე.
   * **რამ შეიძლება გააფუჭოს?:** UI Design System-ის გლობალურმა განახლებამ ან ტეგების გადარქმევამ.

5. **`$("app-cookie-consent button.primary")`**
   * **რატომ არის სტაბილური?:** იყენებს Cookie კომპონენტისა (`app-cookie-consent`) და TBC Design System-ის სემანტიკურ `primary` კლასს, რაც ცალსახად მიუთითებს დათანხმების ძირითად ღილაკზე. სელექტორი სრულად დამოუკიდებელია საიტის ენისგან (KA/EN) და ტექსტის ცვლილებისგან.
   * **რამ შეიძლება გააფუჭოს?:** Cookie კომპონენტის DOM სტრუქტურის ან Design System კლასების გლობალურმა რეფაქტორინგმა.

### Locator Priority Matrix:
1. **ID / Unique Functional Attributes:** `#id`, `[formcontrolname]`, `[mapid]` *(უმაღლესი პრიორიტეტი)*
2. **Semantic Structural Attributes:** `a[href*='...']`, `button[type='submit']`
3. **Component Specific BEM Classes:** `.currency-calculator__swap__button`
4. **Accessible Text Selectors:** `byText(...)` (მხოლოდ დინამიური/ლოკალიზებული ელემენტებისთვის)
5. **Absolute XPath:** *(0% გამოყენება)*

## 3 Flaky Test Awareness - 25 pts

### არჩეული ტესტი: `MoneyTransfersTest` & `CurrencyTest`

ტესტირების პროცესში ერთ-ერთი მთავარი გამოწვევა იყო **Flaky Tests** (ტესტები, რომლებიც ხან გადიან, ხან ფეილდებიან კოდის ცვლილების გარეშე).

### Flakiness-ის წყაროები:
1. **Cookie Banner Interception (`ElementClickInterceptedException`):** Single Page Application (SPA) არქიტექტურის გამო, მობაილ რეჟიმში გვერდების გადართვისას `app-cookie-consent` ბანერი ხელახლა რენდერდებოდა და ფარავდა ეკრანის ქვედა 40%-ს, რის გამოც Selenide-ის ქლიქი ხვდებოდა Cookie-ს ღილაკს და არა სამიზნე ელემენტს.
2. **Encoding Mismatch (Character Corruption):** Windows/Maven გარემოში ქართული ასოებით ძებნისას (`byText("გზავნილები")`), ენკოდინგის აცდენის გამო ტექსტი გარდაიქმნებოდა `?????????`-ად, რაც იწვევდა `NoSuchElementException`-ს.
3. **Asynchronous SPA Hydration:** Angular-ის კომპონენტების ჩატვირთვის დაგვიანება ეკრანის ზომის ცვლილებისას (Mobile emulation).

### როგორ ავიცილეთ თავიდან:
* **გლობალური ჰენდლერი `@BeforeMethod`-ში:** Cookie-ს დახურვის ლოგიკა გადავიტანეთ `@BeforeMethod`-ში `BaseTest.java`-ში. ყოველი ტესტ-მეთოდის წინ ამოწმდება ბანერის არსებობა Duration.ofSeconds -ის დახმარებით.
* **UTF-8 ენკოდინგის სტანდარტიზაცია:** `pom.xml`-ში დაემატა მკაცრი UTF-8 პარამეტრები `maven-surefire-plugin`-ისთვის (`<argLine>-Dfile.encoding=UTF-8</argLine>`), რამაც სრულად აღმოფხვრა სიმბოლოების გაფუჭება.
* გამოვიყენე Selenide-ის `Condition.visible`, `scrollIntoView()` და საჭიროების შემთხვევაში `ClickOptions.usingJavaScript()`, რაც უზრუნველყოფს ელემენტის მზაობას დაჭერამდე.

## 4 Mobile is not Desktop 

### არჩეული სცენარები: MoneyTransfersTest (KAN-T5) & LoansTest (KAN-T4)

###  მობილურისთვის დამახასიათებელი ქცევა
1. **დამალული ნავიგაცია (Hamburger Menu):**
* Desktop: სესხებისა (Loans) და ფულადი გზავნილების (Money Transfers) გვერდების ლინკები პირდაპირ ჰედერში ან მთავარ მენიუშია ღიად განთავსებული.
* Mobile: ორივე პროდუქტის ნავიგაცია სრულად დამალულია მობილურ ბურგერ-მენიუში. ავტომატიზებულმა ტესტებმა ორივე სცენარში ჯერ უნდა გახსნან ბურგერ-მენიუ, დაელოდონ მენიუს გაშლას და მხოლოდ ამის შემდეგ დააჭირონ შესაბამის შიდა ლინკებს (a[href*='/other-products/money-transfers'] ან სესხის განყოფილებას).
* 
### Different Assertions:
* **Desktop:** მოწმდება ელემენტის ჰორიზონტალური განლაგება, Hover ეფექტები და რუკის/კალკულატორის ერთდროული გამოჩენა ეკრანზე.
* **Mobile:** მოწმდება `Burger Menu`-ს გახსნილი მდგომარეობა, Sticky ელემენტების (Chat, Cookie) მიერ კლიკაბელური ზონების გადაფარვის არარსებობა და Viewport-ის ფარგლებში ელემენტების ჩატევა.

### მომხმარებლის გამოცდილების რისკები:
* **Touch Target Size & Overlap:** პატარა ეკრანზე Floating Chat icon ან Cookie ბანერი ხშირად ფარავს მთავარ Action ღილაკებს („მოითხოვე სესხი“, „გადარიცხვა“), რამაც შეიძლება შეაფერხოს კონვერტაცია.
* **Viewport Overflow:** არასწორად დაფორმატებული ცხრილები ან კალკულატორები იწვევენ ეკრანის ჰორიზონტალურ სქროლს (Horizontal Scroll Bug), რაც ამახინჯებს მობილურ ინტერფეისს.


## 5 Design Patterns & Advanced Architecture

პროექტის არქიტექტურაში გამოყენებულია რამდენიმე QA Automation Design Pattern-ი კოდის მასშტაბირებადობისა და ეფექტურობისთვის:

###  TestNG `@Factory` Pattern (Dynamic Test Generation)
`LoansFactory` და `MoneyTransfersFactory` კლასებში გამოყენებულია TestNG-ის **`@Factory`** ანოტაცია.
ამ პატერნის მეშვეობით ხდება ტესტ-კლასის ინსტანციების დინამიური გენერაცია სხვადასხვა საწყისი მონაცემთა ნაკრებისთვის (Data-Driven Execution).
* **უპირატესობა:** ერთსა და იმავე ტესტურ ლოგიკას არ სჭირდება კოდის დუბლირება. Factory იღებს მონაცემთა მასივს და იძახებს ტესტ-ინსტანსებს პარალელურ thread-ებში, რაც უზრუნველყოფს იზოლირებულ და დამოუკიდებელ ტესტ-შესრულებას.

### Page Object Model (POM) & Component Object Model
* **POM:** თითოეული ვებ-გვერდისთვის შეიქმნა შესაბამისი Page კლასი (`CurrencyPage`, `LoansPage` და ა.შ.), სადაც ინკაფსულირებულია ლოკატორები და გვერდის სპეციფიკური ქმედებები.
* **BaseTest Logic:** იერარქიული მემკვიდრეობითობა (`extends BaseTest`), სადაც მართულია ბრაუზერის ინიციალიზაცია, პროფილები (`desktop`/`mobile`) და გლობალური Pop-up ჰენდლინგი.
